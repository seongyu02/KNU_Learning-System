## 1. 사용자의 목표

사용자는 강남대학교 이러닝캠퍼스에서 과제와 강의 일정을 읽어와 미리 확인할 수 있는 웹사이트를 제작하고 배포함. 현재는 본인 소유의 인증 키를 사용해 본인의 데이터만 볼 수 있음.

### 최종 요구사항

1. 별도 회원가입 없이 강남대학교 학교 계정으로 로그인할 수 있을 것.
2. 학생 A가 로그인하면 학생 A의 강의·과제·마감일만, 학생 B가 로그인하면 학생 B의 정보만 보일 것.
3. 기존 화면과 D-Day, 캘린더, 과목 필터 및 동기화 기능을 최대한 유지할 것.
4. 가능한 한 학생이 별도의 iCal URL이나 키를 복사·등록하지 않아도 되도록 할 것.
5. 배포 URL은 공개하지 않으며, 소스코드와 스크린샷을 이용해 개발 방향을 검토할 것.

### 핵심 구분

- **학교 계정 인증:** 외부 웹사이트에서 강남대학교 로그인으로 해당 학생의 신원을 확인하는 문제.
- **LMS 데이터 접근:** 인증된 학생의 수강 과목·과제·강의 데이터를 외부 서비스가 적법한 권한으로 읽는 문제.

이 두 기능은 별개이다. 학교 SSO 로그인에 성공한다고 해서 자동으로 LMS 데이터 조회 권한이 생기는 것은 아니다.

## 3. 업로드한 프로젝트에 관해 대화에서 분석한 사항

2026-11-10에 사용자가 KNU_Learning-System.zip을 업로드했고, 이전 답변에서는 다음 구성으로 분석했다고 설명했다.

| 구분 | 이전 답변에서 설명한 구현 |
|---|---|
| 프론트엔드 | HTML + JavaScript |
| 백엔드 | Cloudflare Workers |
| DB | Cloudflare D1 (SQLite 기반) |
| 배포 | Cloudflare Workers |
| LMS 데이터 소스 | Moodle iCalendar(iCal) 피드 |
| 앱 접근 인증 | APP_TOKEN, VIEW_TOKEN |
| 정기 동기화 | Cloudflare Cron Trigger |
| 다중 사용자 | 미구현 |

### 기존 데이터 흐름

```
강남대학교 이러닝캠퍼스
  └─ 본인의 개인 iCal 일정 URL (ICS_URL)
      └─ Cloudflare Worker가 일정 다운로드·파싱
          └─ Cloudflare D1에 일정 저장
              └─ 프론트엔드에서 과제·강의·마감일 표시
```

이 분석에 따르면 기존 서비스는 학교 ID·비밀번호로 매번 자동 로그인하는 방식이 아니라 개인 iCalendar 피드를 가져오는 방식이다.

### 당시 답변이 언급한 파일·코드 위치

- `내과제/일정가져오기.py`: 일정 가져오기 처리.
- `deploy/src/worker.js`: Worker API, 일정 동기화, 인증 및 화면 응답.
- `deploy/schema.sql`: D1 데이터베이스 테이블 정의.
- `내과제/웹앱.html`: 화면 구현.
- `내과제/.env.local`: iCal URL, 앱 토큰 등 환경변수.
- `내과제/계기판 열기.url`: 당시 분석에서 접근 토큰이 포함된 주소가 있다고 지적한 파일.

기존 답변에서 지목한 주요 수정 구간:

| 당시 언급한 구간 | 설명 | 변경 방향 |
|---|---|---|
| worker.js 130~170행 | 단일 ICS_URL 처리 | 사용자별 연동 URL 및 동기화 |
| worker.js 197~205행 | 공통 APP_TOKEN / VIEW_TOKEN 인증 | 사용자별 인증 세션 |
| worker.js 328~379행 | 공통 DB 조회·수정 | 사용자 식별자 기준 권한 제한 |
| schema.sql | 일정/로그의 사용자 구분 부족 | user_id 도입 |
| worker.js 284~286행 | 한 계정의 예약 동기화 | 학생별 동기화 작업 |

※ 행 번호는 이전 응답에서 제시한 참고값이며, 실제 현재 소스 상태에 따라 다를 수 있음.

### 언급된 보안 이슈

- ICS_URL은 해당 학생의 일정 데이터에 접근할 수 있는 민감한 비밀 URL이므로 보호해야 함.
- APP_TOKEN, VIEW_TOKEN 등 공통 토큰을 여러 학생에게 공유하는 방식은 부적절함.
- ZIP 안에 .env.local 등의 실제 자격 증명이 포함되어 있다면 공개 저장소에 그대로 업로드하면 안 됨.
- 브라우저용 JavaScript에 권한 토큰을 삽입하는 구조라면 토큰 노출 여부를 점검해야 함.
- 이미 외부로 노출된 토큰이 있다면 회전(교체)하고 개인 일정 URL의 폐기·재발급 가능성을 확인해야 함.
- .gitignore는 Git 추적만 제외하며, 수동으로 만든 ZIP 내부 파일까지 자동 제거하지 않음.

## 4. 검토한 구현 방식

### 방식 A — 학교 공식 SSO + 학생별 LMS API 연동 (최종 희망 방식)

```
학생
  → 기존 과제 관리 웹사이트에서 '강남대학교 계정으로 로그인' 클릭
  → 강남대학교 공식 인증 페이지에서 계정 인증
  → 외부 웹사이트가 인증 결과를 검증하고 세션 생성
  → 학생에게 허가된 LMS API 또는 연동 권한으로 데이터 조회
  → 해당 학생의 과제·강의·마감일 대시보드 표시
```

- 장점: 별도 회원가입이 필요 없고, 학교 로그인만으로 개인별 서비스 사용 가능.
- 전제: 학교에서 외부 서비스 SSO 연동을 허용하고 필요한 인증 규격과 등록 절차를 제공해야 함.
- 추가 전제: LMS가 학생별 강좌·과제에 접근할 수 있는 API 또는 동등한 적법한 연동 수단을 제공해야 함.
- 미확인: 강남대학교가 외부 개인 개발 웹사이트에 OIDC, OAuth 2.0, SAML 등의 연동을 제공하는지, 학생별 데이터 접근 API를 허용하는지.
- 주의: Moodle 자체의 API 존재가 곧 강남대학교 인스턴스의 외부 API 사용 허용을 뜻하지는 않음.

이 방식이 사용자가 마지막으로 명확하게 요청한 목표이다.

### 방식 B — 별도 앱 로그인 + 학생별 iCal URL 연결 (대안)

```
학생별 웹사이트 로그인
  → 본인이 이러닝캠퍼스에서 개인 iCal URL 발급
  → 최초 1회 웹사이트에 연결
  → 서버가 사용자별 iCal 피드 동기화
  → 사용자별 대시보드 표시
```

- 기존 구조를 재활용하기 상대적으로 쉬움.
- 학교 ID·비밀번호를 서비스 서버에 저장할 필요가 없음.
- 단점은 별도의 회원가입/로그인 및 최초 iCal 연결 과정이 필요할 수 있다는 것.
- 사용자는 나중에 이 방식이 아닌 학교 계정 로그인만으로 사용하는 방식을 희망한다고 명확히 밝혔음.

### 방식 C — 브라우저 확장 프로그램

학생이 학교 사이트에 직접 로그인한 상태에서 브라우저 확장 프로그램이 허용된 페이지의 정보를 읽고 웹사이트로 동기화하는 방식도 대안으로 논의됨.

- 학교에서 외부 SSO·API를 제공하지 않는 경우 검토할 수 있음.
- 단, 브라우저 확장 설치 및 실행에 의존하고 학교 정책·사용자 동의·보안 준수가 필요함.
- 학교 계정으로 외부 사이트에 자동 로그인하는 공식 SSO와는 다름.

### 피해야 하는 방식

학생의 학교 ID와 비밀번호를 임의의 외부 웹사이트에 직접 입력받아 저장하고, 이를 이용해 학교 로그인 과정을 자동화하는 방법은 개인정보와 계정 보안상 위험이 높으므로 권장하지 않음.

## 5. 다중 사용자 구조 변경 제안

### 서버 API 예시

```
GET  /api/me/assignments
GET  /api/me/courses
POST /api/me/sync
```

서버는 요청의 인증 세션으로 사용자 신원을 검증하고 해당 user_id의 데이터만 조회·수정해야 한다. 클라이언트가 임의로 보낸 user_id만 믿고 접근을 허용하면 안 된다.

### 기존 단일 키 구조의 개념적 예시

```python
LMS_TOKEN = os.getenv("MY_LMS_TOKEN")

def get_assignments():
    return fetch_lms_data(LMS_TOKEN)
```

### 사용자별 권한으로의 개념적 변경

```python
def get_assignments(user_id):
    connection = get_user_lms_connection(user_id)
    return fetch_lms_data(connection)
```

위 코드는 설계 개념을 설명하기 위한 의사코드이며 실제 ZIP에서 확인된 구현 코드를 그대로 옮긴 것은 아니다. get_user_lms_connection은 반드시 학교가 허용한 적절한 방식으로 권한을 확보해야 한다.

### 데이터베이스 관점

- 사용자 식별 테이블 또는 인증 제공자의 고유 사용자 ID 관리.
- items, logs 및 필요한 연결 정보에 사용자 소유권을 나타내는 user_id 추가.
- 모든 조회·수정·삭제·동기화 요청에 사용자별 접근 제어 적용.
- 같은 과목·같은 과제 제목을 서로 다른 학생이 가진 경우 ID가 충돌하지 않도록 사용자별 키 또는 복합키 설계.
- 기존 데이터와 관리자 계정에 대한 마이그레이션 마련.
- SSO로 사용자 식별이 가능하다면 학생이 따로 가입 폼을 작성할 필요 없이 최초 로그인 시 서버 내부의 사용자 레코드를 자동 생성할 수 있음.

### 동기화 관점

- 기존의 단일 ICS_URL 기반 Cron 처리에서 사용자별·권한별 데이터 갱신 구조로 변경.
- 사용자의 연결 해제·로그아웃·권한 만료·실패 시나리오 처리.
- 가능하면 비밀번호 대신 학교가 승인한 액세스 토큰 사용.
- 민감한 토큰은 프론트엔드에 전달하거나 로그에 남기지 않고 서버 측에서 안전하게 보호.

## 6. 현재 확정된 결론과 미확인 사항

### 대화에서 확정된 사용자 요구

- 기존 서비스를 다른 학생도 사용할 수 있게 만들고 싶다.
- 학교 계정 로그인만 요구하고, 별도의 회원가입은 원하지 않는다.
- 학생별 본인의 강의와 과제만 가져와야 한다.
- 가능한 한 기존 대시보드 디자인과 기능을 유지하고 싶다.
- 배포 주소는 공개할 수 없지만 소스 ZIP은 제공했다.

### 기술적으로 가능한 점

- 현재 Worker + D1 기반 서비스를 사용자별 데이터로 확장하는 설계는 가능하다.
- 학교가 공식 SSO 및 사용자별 데이터 접근 수단을 지원하면 별도 회원가입 없는 방식으로 구현할 수 있다.
- 그러나 강남대학교 환경에서 실제 사용 가능한지 여부는 학교의 공식 지원과 승인이 확인되어야 한다.

### 아직 확인할 수 없는 점

1. 강남대학교가 외부 학생 개발 프로젝트의 SSO 연동을 허용하는지.
2. 연동 프로토콜이 OIDC, OAuth 2.0, SAML 또는 다른 규격인지.
3. 외부 앱 등록에 필요한 승인·보안·개인정보 처리 조건.
4. 사용자별 강좌·과제·강의 정보에 접근할 수 있는 공식 LMS API 제공 여부.
5. 학교 SSO 인증으로 발급받은 토큰이 LMS API 접근 권한까지 포함하는지.
6. 영상 강의 진행률, 과제 제출 상태 등 iCal에 없는 정보의 제공 여부.

따라서 '학교 홈페이지에 SSO 로그인 버튼이 있다'는 사실만으로 외부 웹사이트에서 학교 계정 로그인과 모든 학생의 LMS 데이터 조회를 자동 구현할 수 있다고 단정할 수는 없다.

## 7. 권장 후속 작업

1. 강남대학교 LMS 운영 담당 부서 또는 학교 정보시스템 담당 부서에 외부 웹앱의 학교 SSO 연동 지원 여부 확인.
2. 외부 앱 등록 절차, 리디렉션 URI 등록, 인증 프로토콜, 사용 가능한 사용자 식별 정보 확인.
3. 학생별 LMS 읽기 전용 API의 존재와 접근 권한, 이용약관 및 개인정보 처리 조건 확인.
4. 두 연동 모두 가능하면 기존 Cloudflare Worker에 SSO 콜백과 인증 세션 처리 추가.
5. D1 스키마 및 CRUD API를 user_id 기준으로 분리하고 기존 1인용 데이터 마이그레이션.
6. 학교 SSO는 가능하지만 LMS API가 없다면 학교 승인 하에 개인 iCal 연동 등의 보완책 검토.
7. SSO/공식 API 모두 불가능하면 사용자가 원하는 '학교 계정 로그인 한 번에 자동 연동' 요구는 기존 코드만으로 보장할 수 없음을 명확히 안내.

### 문의할 질문 초안

> 강남대학교 이러닝캠퍼스의 강의 및 과제 일정을 개인별로 보여주는 학생 개발 웹서비스를 만들고 있습니다. 학생들이 별도 회원가입 없이 강남대학교 공식 계정으로 로그인할 수 있도록 외부 서비스 SSO 연동(OIDC/OAuth/SAML 등)을 지원하는지 문의드립니다. 또한 사용자 동의 및 인증을 기반으로 본인의 수강 강좌, 과제 일정, 강의 일정을 읽기 전용 API로 조회할 수 있는지, 가능하다면 서비스 등록과 승인 절차를 알려주시면 감사하겠습니다.
