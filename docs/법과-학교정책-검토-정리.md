# 법·학교 정책 검토 — 정리 (2026-11-14)

> Claude Code 와 한 검토를 정리한 것이다. 변호사의 자문이 아니다 — 공개된 판례·조문·학교 페이지를 읽고 정리했고,
> 확인하지 못한 것은 맨 아래에 따로 적었다.
> 서버가 학교 쪽에 하는 일은 [worker.js](../deploy/src/worker.js) 와 [deploy/README.md](../deploy/README.md) 에 있다.
> 학번·비밀번호·달력 주소·토큰·배포 주소는 이 문서에 적지 않는다.

## 질문

> "우리 이거 할때 강남대학교 내용을 우리가 막 긁어오는건데 법적으로 문제나 정책에 문제가 없나"

## 결론

내용을 가져오는 것 자체는 걱정이 적다. 걸리는 것은 **다른 학생의 학교 비밀번호를 이 서버가 받아 대신 로그인하는 부분**이다.
불법이라고 못 박을 근거는 찾지 못했지만 학교가 허락한 적도 없다. 회색 지대다.

무엇을 할지는 아직 정하지 않았다 — 아래 "할 수 있는 일" 절. 사용자가 정하면 거기에 적는다.

## 서버가 학교에 하는 일

코드에서 확인했다(2026-11-14, 운영 버전 `9cb7a4a7`).

| 언제 | 학교에 보내는 요청 | 무엇으로 들어가나 |
|---|---|---|
| 학생이 로그인할 때 한 번 | 로그인 → 달력 내보내기 주소 받기 → 과제가 걸린 날의 달력 화면 읽기(정확한 마감 시각) → 로그아웃. 모두 합쳐 많아야 30여 번(시각을 찾는 요청은 30번이 한도) | 학생이 넣은 아이디·비밀번호. 요청이 끝나면 버린다 |
| 그 뒤 | 달력 파일(iCal) 하나 | 이캠퍼스가 내준 달력 내보내기 주소. 비밀번호도 학교 세션도 없다 |

- "그 뒤"가 도는 때: 로그인 직후, 화면을 열었는데 6시간 넘게 묵었을 때, `지금 동기화` 단추(30초에 한 번), 매시 13분에 가장 오래 안 돈 5명.
- 가져오는 것: 로그인한 학생 본인의 일정(과제·강의 제목, 과목 이름, 날짜·시각)과 화면 위쪽에 적힌 본인 이름.
  강의 자료·영상·성적·다른 학생의 정보는 가져오지 않는다.
- 저장하는 것: 학번, 이름, 일정 목록, 암호화한 달력 주소. 비밀번호와 학교 세션은 저장하지 않는다.
- 요청에는 `deadline-dashboard` 라는 이름표(User-Agent)를 붙인다. 브라우저인 척 숨기지 않는다.
- 운영 서버에 등록된 사람은 4명이다(2026-11-14, 숫자만 셌다).

| 전산정보원 정보보안 게시판 | 보안 권고 글 | 계정·접근에 관한 규정 |
| 원격교육지원센터 홈페이지 | 이캠퍼스 안내·매뉴얼·공지 메뉴 | 규정 메뉴, 계정 공유·자동 프로그램을 금지하는 문구 |

제3자가 이용하도록 해서는 아니 된다." 어기면 계정 이용을 제한할 수 있다(같은 조 ③). 강남대의 규정은 아니다.

## 판단

### 걱정이 적은 부분

- 가져오는 것이 로그인한 학생 본인의 일정뿐이다. 남의 정보도, 학교가 만든 강의 자료도 아니다.
- 주기적으로 받는 달력 파일은 이캠퍼스(무들)가 바깥 달력 앱에 넣어 쓰라고 내주는 주소에서 받는다. 만든 뜻대로 쓰는 것이다.
- 요청이 적어 학교 서버에 부담을 주지 않는다.
- 돈을 받지 않고, 가져온 것을 남에게 넘기지 않는다.
- 학교가 공개해 둔 것(robots.txt, 로그인 화면, 처리방침) 어디에도 이런 접근을 막는 문구가 없다.
- 로그인 화면에 공식 서비스가 아니라는 것, 비밀번호를 저장하지 않는다는 것, 무엇을 저장하는지를 적어 두었다.

### 걸리는 부분

1. **대신 로그인.** 2005도870 의 원칙대로면 접근권한은 학교가 정하는데, 학교는 이 서버에 권한을 준 적이 없다.
   예외 ①(학생의 심부름꾼)에 든다고 볼 근거는 있다 — 학생이 직접 시키고, 그 학생의 일정만 가져와, 그 학생에게만 보여 준다.
   하지만 법원이 이런 서비스에 그렇게 판단한 예를 찾지 못했다. 벌칙이 무거운 조항이라 "아마 괜찮다"로 넘길 일은 아니다.
2. **학교 규정.** 강남대의 계정·정보보안 규정을 찾지 못했다. 있다고 보고 움직이는 편이 안전하다 — 강남대 입학처 약관도,
   다른 대학의 규정도 계정을 남에게 알려 주지 못하게 한다. 그렇다면 규정을 어기는 것은 형식상 이 서비스에 비밀번호를 넣은
   학생이다. 비밀번호 찾기가 학교 통합 로그인으로 이어지는 것을 보면 이 비밀번호는 학교의 다른 시스템에도 통할 가능성이
   크고(확인하지 않았다), 학교가 가장 꺼릴 지점이 여기다.
3. **개인정보.** 운영하는 사람이 개인정보처리자에 해당할 수 있다. 지금 있는 것은 로그인 화면의 안내 세 줄,
   `내 데이터 삭제` 단추, 달력 주소 암호화다. 없는 것은 동의 표시와 처리방침(보관 기간, 문의처)이다.
4. **사고가 났을 때.** 서버나 Cloudflare 계정이 털리면 로그인하는 학생의 학교 비밀번호가 새어 나갈 수 있다
   ([deploy/README.md](../deploy/README.md) 에 적어 둔 것). 그때의 책임은 위 셋보다 훨씬 크다.
   Cloudflare 계정 2단계 인증이 그래서 중요하다.

일이 생긴다면 가장 있을 법한 것은 학교가 알게 되어 그만하라고 하거나 접속을 막는 것이라고 본다(추정이다).

## 할 수 있는 일

아직 정하지 않았다.

| 할 일 | 풀리는 것 | 드는 것 |
|---|---|---|
| 개인정보 안내와 동의를 로그인 화면에 넣는다(무엇을·왜·언제까지 보관하는지, 지우는 법, 문의처) | 걸리는 부분 3 | 화면 수정 한 번 |
| 학교에 묻는다 — 원격교육지원센터(이캠퍼스 담당), 전산정보원(계정·보안 담당), 또는 담당 교수 | 걸리는 부분 1·2. 학교가 좋다고 하면 예외 ②·③에 든다 | 문의 한 번. 하지 말라는 답이 올 수 있다 |
| 답이 오기 전에는 서비스를 더 알리지 않는다 | 위험이 커지지 않는다 | 없음 |
| Cloudflare 계정 2단계 인증을 켠다 | 걸리는 부분 4 | 사용자가 한 번 |
| (학교가 안 된다고 하면) 비밀번호를 받지 않는다 — 학생이 이캠퍼스에서 달력 내보내기 주소를 복사해 붙여 넣는다 | 걸리는 부분 1·2 가 거의 사라진다 | 가입할 때 손이 한 번 더 간다. 정확한 마감 시각 보정이 빠진다 |

## 확인하지 못한 것

- 강남대의 정보보안·계정 관리 규정 본문. 공개된 곳에서 찾지 못했다. 전산정보원에 물어야 안다.
- 이캠퍼스에 로그인한 뒤에만 보이는 약관·동의 화면이 있는지. 사용자 계정으로 대신 로그인하지 않으므로 보지 않았다.
- 이캠퍼스 비밀번호가 학교 통합 계정 비밀번호와 같은 것인지.
- 비슷한 학생 서비스를 학교가 막은 사례. 찾지 못했다.
